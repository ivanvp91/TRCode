# TRCode 0.1.7: аудит функций, media и конкурентных преимуществ

> Этот документ описывает состояние до исправлений. Результат последующего исправления и окончательные проверки: [2026-10-04-fixes.md](2026-10-04-fixes.md). Исходные воспроизведения сохранены как историческое свидетельство; `scripts/audit-repro.mjs` теперь проверяет корректное поведение после исправлений.

Дата: 4 октября 2026. Основа: commit `ecf0f71` и текущая рабочая копия. В ней до аудита уже изменён `src/ui/repl.ts`; это учтено отдельно в CORE-12. Исходники приложения в ходе аудита не исправлялись. Добавлены этот отчёт, воспроизводящий скрипт и его JSON-результаты.

## Вывод

У TRCode широкая функциональная база: несколько протоколов и провайдеров, переключение моделей, учёт токенов, оптимизация контекста, MCP, skills, память, субагенты, brain/swarm/orchestration, goals и media. Но широта возможностей сейчас опережает надёжность исполнения. Заявлять превосходство во всех функциях пока нельзя.

Самые важные проблемы — потеря данных при откате, запуск оставшихся инструментов после отмены, обход разрешений через code mode и недостаточная надёжность платной генерации. Для media главным улучшением должен стать полный цикл: **сформировать требования → подобрать возможности модели → создать → проверить → исправить в пределах бюджета → сохранить результат и возможность продолжения**.

«Идеален во всём» следует превратить в проверяемые требования к каждому сценарию. Без этого новые команды увеличивают площадь багов, а обещания качества остаются субъективными.

## Дополнительные находки при чтении кода

Эти пункты подтверждены устройством кода, но не включены в 25 runtime-воспроизведений.

1. **Общий cost не включает media.** `ToolResult`/`ToolContext` не передают usage/cost генерации в `UsageTracker`; media помещает цену в текст, а loop учитывает только ответ текстовой модели. `/cost`, `/stat` и цена выполнения задачи могут существенно недооценивать счёт. Нужны typed billing events для chat, media, retry и partial jobs.
2. **Video jobs существуют в closure.** `Job` живёт только в текущем tool call. Нет durable journal, команды продолжения или скачивания по сохранённому job id. Esc прекращает ожидание, но не отменяет счёт у провайдера. В API-сообщении иногда есть id; это не полноценный механизм восстановления.
3. **Capabilities недостаточно надёжны.** Для видео ограничения перечислены в prompt, но tool не проверяет их. Для image provider-level `ACCEPTS` выдаёт возможности хоста за возможности модели. Каталог изображения сообщает объединение параметров нескольких endpoints, тогда как окончательные capabilities/prices существуют на уровне выбранного endpoint. Нужна модель + endpoint + версия capabilities. [OpenRouter: Image Generation](https://openrouter.ai/docs/guides/overview/multimodal/image-generation).
4. **Обрезание требований происходит после оплаты.** Image предупреждает об отброшенных параметрах лишь в конце. Нельзя молча потерять существенное требование «прозрачный фон», «без звука», «последний кадр именно этот». Разделить обязательные требования и допустимые defaults.
5. **Video reference-to-video отсутствует.** В tool есть first/last frame, но нет `input_references`. В prompt предлагается описать персонажа/стиль словами, что ухудшает сохранение идентичности. OpenRouter уже имеет отдельный механизм визуальных references. [OpenRouter: Video Generation](https://openrouter.ai/docs/guides/overview/multimodal/video-generation).
6. **Загрузка и сохранение не образуют безопасную транзакцию.** `downloadTo` держит всё видео в памяти; image URL fetch не имеет своего timeout; нет общего byte limit, checksum, atomic output и recoverable partial download. Image/audio disk errors выходят из tool без сохранённого provider-result manifest. При нескольких картинках частично сохранённые пути не возвращаются при следующей ошибке.
7. **`read_image` ограничен для качественного QA.** Предел 1.6 MB без автоматического downscale/crop; JPEG/WebP dimensions не извлекаются; BMP может оказаться не принят конкретным vision API. Нужны decoder, pixel budget и preview variants, оригинал сохранять отдельно. Описание инструмента также противоречиво: обещает metadata-first, реализация по умолчанию отправляет pixels.
8. **Audio — пока генерация, а не полный звуковой режим.** Нет typed audio input, транскрипции, diarization, timestamps, измерения loudness, playback и проверки произнесённого текста. У `Message` существуют только image attachments. Музыка определяется regexp по имени, voices и PCM sample rate заданы общей таблицей. Нужны provider/model contracts.
9. **Сохранение сессий неатомарное.** `Session.save()` напрямую перезаписывает один JSON и подавляет ошибки; прерывание или ошибка диска могут сделать единственную копию нечитаемой. Нужны atomic replace, backup/journal и видимый degraded state.
10. **Orchestration может пометить неполную работу успешной.** В `src/agent/orchestrator.ts:313` успех = непустой `finalText` и не `aborted`; `max_steps`, `looping` и `length` не отвергаются. Зависимый шаг получает такой результат как установленный факт. Циклы DAG последовательно запускаются вместо явной ошибки; зависимые steps не блокируются автоматически при failure prerequisite.
11. **Cancellation в code mode не охватывает host SDK.** `sdk.web.fetch/search` не получают abort/timeout, SDK shell запускается отдельным дочерним процессом host и не связан с signal. Остановка дочернего JS не гарантирует остановку его уже запущенных операций. Нужен единый scope ресурсов.
12. **MCP требует более точной модели эффектов.** Все tools маркируются `network`, включая потенциально изменяющие внешние данные. Sanitization/truncation имён до 64 символов может дать коллизии. Поддержан stdio transport; более широкую совместимость необходимо расширять и проверять отдельно.

## Оценка основных функций

Это оценка зрелости по реализации и локальной проверке, а не численный benchmark производительности.

| Функция | Что уже полезно | Что требуется до высокого стандарта |
|---|---|---|
| Провайдеры и протоколы | OpenAI Chat, Responses, Anthropic adapters; выбор хостов, сохранение модели/effort | Версионированные contract fixtures, live smoke для каждой поддержанной связки, точная совместимость Gemini/прочих endpoint |
| OAuth/API keys | Разделение provider credentials, refresh, проверка логина | OS credential store по возможности, atomic token refresh, тесты конкурирующего refresh и полного redaction |
| Переключение моделей | В одной сессии, provider state и project state | Проверка совместимости истории/attachments/tools и немедленное обновление context/cost |
| Агентный цикл | Streaming, reconnect, tool pairs, spill, loop guard | Runtime schema validation, отмена очереди, глобальные ресурсы/бюджет, side-effect provenance |
| Read/write/edit | Diff и read-before-overwrite, CRLF поддержка | Hash guard, atomic writes, file locks, symlink policy, patch-many-files как транзакция |
| Shell | Progress, idle timeout, process-tree kill, часть snapshots | Проверка pre-aborted signal, права на внешние пути, структурированные exit/result, ясное покрытие undo |
| Поиск проекта | Dependency-free glob/grep, ignores, ограниченный вывод | Точный gitignore, ускорение на больших репозиториях, отмена regex-heavy scan, индекс symbols/опциональный rg |
| Контекст и caching | Bound-at-source, spill, projection, stable prompt snapshots | Полный размер запроса: system + schema + text + images + output reserve; compaction внутри длинного turn |
| Sessions/resume/fork | История, возобновление, branch/fork | Crash recovery, атомарность, миграции формата, audit journal |
| Undo/checkpoints | Вне зависимости от пользовательского Git, защита части shell writes | CORE-08, безопасная обработка diverged файлов, гарантия pre-write snapshot, full scope coverage |
| Skills/memory/UI library | Progressive loading и проектный контекст | Разрешение конфликтов инструкций, provenance, тесты качества auto matching, отзыв устаревших правил |

## Что действительно сравнивается с конкурентами

Сравнение документационное, по состоянию доступных официальных страниц на дату аудита. Соревновательные прогоны одинаковых задач не выполнялись. Отсутствие функции в выбранной странице не доказывает её отсутствие через plugins, MCP или новые версии.

| Конкурент | Подтверждённый ориентир | Что это означает для TRCode |
|---|---|---|
| OpenCode | Документирует 75+ providers/local models, granular permissions, опциональную интеграцию LSP | Десять providers и `allow/ask/deny` по пяти risk classes не являются лидерством. Лучше конкурировать качеством совместимости и понятным маршрутом задачи. [Providers](https://opencode.ai/docs/providers/), [Permissions](https://opencode.ai/docs/permissions/), [LSP](https://opencode.ai/docs/lsp/). |
| Claude Code | Checkpoints/resume/rewind существуют; shell modifications и большинство subagent writes не покрываются его rewind | TRCode потенциально выигрывает покрытием своей части shell writes и общим snapshot hook субагентов. Нужно сначала устранить потерю данных, доказать покрытие и сохранять manual edits. [Checkpointing](https://code.claude.com/docs/en/checkpointing). |
| ChatGPT desktop | Документированы subagents и независимые worktrees для параллельной работы | Субагенты уже обычная возможность; общий cwd без защиты writes слабее изоляции worktree. | Aider | Repository map выбирает релевантные части проекта через граф зависимостей и token budget | Один list + grep не доказывает лучшую работу с большим репозиторием. Нужны контекстный индекс/карта и benchmark успешных изменений. [Repository map](https://aider.chat/docs/repomap.html). |

Уже подтверждённые достоинства TRCode: небольшой runtime без npm-зависимостей, явные per-host adapters, прозрачная структура token projection, инструменты media в том же процессе, независимые read-only исследовательские режимы. Это полезные свойства, но отсутствие зависимостей не является самостоятельной мерой качества. Decoder, sandbox и media tooling могут оправдать добавление ограниченных зависимостей.

Потенциальные преимущества, которые стоит доказать: более низкая цена успешной задачи за счёт выбора подходящей модели; единый воспроизводимый workflow кода и media; восстановление оплаченного job после любой локальной ошибки; объяснимый полный счёт; безопасный undo параллельной работы.

## Как сделать image качественным

1. **Условие результата.** Хранить brief: что изображено, обязательный текст, язык, размеры, ratio, прозрачность, стиль, что нельзя менять. Текст не переводить вместе с английским prompt.
2. **Выбор модели по задаче.** Точная надпись, фотореализм, vector, edit/mask, character consistency — разные capabilities. Пользователь задаёт цель и бюджет; ручной выбор модели остаётся override.
3. **References как управляемые объекты.** Source image, identity reference и style reference имеют разные роли; показывать thumbnails и порядок. Добавить region/mask editing там, где поддержано, с честным отказом на остальных моделях.
4. **Проверка до оплаты.** Все must-have должны сохраняться в итоговом запросе. Не поддержан transparent PNG — подобрать допустимую модель либо сообщить ограничение до генерации. Проверять reference count, mime, dimensions и реальные endpoint options.
5. **Автоматическое QA.** Decoder, размеры, alpha, OCR обязательного текста, vision-проверка содержания. Автоматическая оценка может ошибаться; визуальная оценка и утверждение пользователя остаются частью творческих задач.
6. **Избирательная правка.** Поправить надпись/руку/фон отдельно, сохранив удачные элементы. Одна генерация — default, дополнительные итерации — в заранее согласованном лимите.
7. **Артефакт.** Оригинал, preview, brief, итоговый prompt, model/endpoint, references hashes, параметры, revised prompt, cost и версия. `seed` использовать только при поддержке; он не гарантирует идентичность результата на всех hosts.

Возможное превосходство: пользователь получает проверенный пригодный asset и управляемые локальные правки, а история вариантов позволяет вернуться к предыдущему результату. На одних и тех же моделях это измеряется лучше, чем субъективное обещание «наш prompt красивее».

## Как сделать video качественным

1. **Разделить замысел и операции.** `/video` открывает project workflow. Сообщения «измени музыку», «объясни цену», «продолжи job» не должны автоматически создавать новый ролик; текущая инструкция трактует каждое сообщение как generation request.
2. **Brief → storyboard.** Для каждой сцены: длительность, субъект/действие, камера, свет, переход, dialogue/sound. Для простого клипа один shot; длинные ролики — несколько коротких контролируемых сцен. Не заставлять один prompt реализовывать сложный фильм.
3. **Сохранение идентичности.** Reference-to-video, first/last frame, keyframes и character/style assets по возможностям модели. Требования к движению и continuity хранить отдельно от prose prompt.
4. **Дешёвый review этап.** Сначала storyboard/keyframes/previews; дорогие финальные renders только после выбора, если сценарий это оправдывает. Не делать скрытое платное размножение вариантов.
5. **Persistent job manager.** Локальный journal до/после submit, known job id, status/retry, возобновление polling/download после перезапуска. Состояние ambiguous-submit должно требовать reconciliation, а не повторной оплаты.
6. **Разделить отмену.** Stop waiting и cancel provider job — разные действия. Если provider не поддерживает cancel, сообщить, что задача продолжает выполняться, и сохранить способ забрать результат.
7. **QA ролика.** `ffprobe` и декодирование: duration, fps, width/height, streams, codec. Contact sheet и выбранные motion frames: continuity, мерцание, логотип/надписи, неподвижные кадры. Audio QA отдельно. Не утверждать, что несколько кадров гарантируют отсутствие дефектов между ними.
8. **Монтаж и delivery.** Опциональный ffmpeg backend: trim, concat, sound mix, subtitles, logo overlay, H.264/AAC MP4 preset, вертикальный/горизонтальный exports. Текст и логотипы, требующие точности, зачастую лучше наложить детерминированно после генерации.
9. **Правка конкретной сцены.** Перегенерировать только неудачный shot, сохранить остальное; edit/extend через provider capabilities либо явный локальный монтаж.

Job model должен различать `planned`, `submitting`, `submitted`, `running`, `completed_remote`, `downloading`, `verifying`, `ready`, `failed`, `cancel_requested`, `cancelled`, `unknown`. Ошибка сети при download не должна уничтожать факт remote completion. Provider status и local execution status хранить отдельно.

## Как сделать audio качественным

1. **Разделить TTS, speech generation, music и audio analysis.** Они имеют разные входы, форматы, voices, sample rate, billing и возможности. Для точного чтения предпочесть dedicated TTS adapter вместо обещания, что chat audio всегда произнесёт текст дословно. OpenRouter документирует отдельные TTS/STT возможности рядом с chat audio. [Audio](https://openrouter.ai/docs/guides/overview/multimodal/audio).
2. **Provider metadata вместо heuristics.** Формат/каналы/sample rate — часть контракта; PCM нельзя безопасно угадать по magic bytes. Music duration, vocals/instrumental, tempo — структурированные возможности модели.
3. **Точное произнесение.** Проверка транскрипции против исходника, словарь произношения имён/чисел/аббревиатур, отдельные проверки русского и украинского текста. Не удалять пробелы/пунктуацию без необходимости, если обещана дословность.
4. **Длинная речь.** Делить по предложениям, сохранять chunks, собирать с короткими crossfades; учитывать, что интонация/тембр могут изменяться между запросами. Повторять только повреждённый chunk в рамках бюджета.
5. **Техническое качество.** Контроль clipping, silence, channels, sample rate, loudness/true peak под выбранный delivery preset. Music loop проверять на слышимую границу. Выбор target громкости задавать продуктовым preset, не общим случайным значением.
6. **Input и просмотр результата.** Transcribe/analyze tools, timed transcript, subtitles, playback и waveform в preview; диктовка задания как отдельная возможность. Для video — синхронизация narration и музыки с timeline.

## Общее основание для media

Существующие маленькие adapters стоит сохранить, но вынести общий lifecycle в отдельный слой, а не разрастить один tool:

```text
brief / requirements
  -> capability resolution + validated request + cost estimate
  -> permission/budget reservation
  -> job journal + provider adapter
  -> remote result / streamed chunks
  -> bounded download + atomic save
  -> deterministic checks + optional model review
  -> artifact manifest + preview + bounded repair
```

Нужны `MediaCapabilities`, `MediaJob`, `MediaArtifact`, `BillingEvent` и `VerificationResult` с версиями. В manifest сохранять hash inputs, provider job id, prompt/params, provider revision если доступен, software versions, фактическую стоимость/unknown и пути. Не сохранять credentials и полные presigned URL в публичный отчёт.

Три группы разрешений должны быть независимы: получить данные из сети; потратить деньги; изменить файл. Лимит пользователя на весь workflow нужно резервировать атомарно между параллельными agents, иначе четыре отдельных разрешённых операции могут превысить общий бюджет.

## Стандарт высокого качества для всех функций

1. **Операционная корректность:** инструмент не объявляет успех без проверенного результата; invalid args не достигают side effects; нет новых действий после abort; явно показывается результат уже начатых операций.
2. **Сохранность:** отказ диска/сети/процесса не уничтожает предыдущую версию файла, сессию или оплаченный job; конфликты пользователя/агентов обнаруживаются.
3. **Завершение задачи:** для code — конкретные checks и artifacts; для media — проверенный файл и соответствие обязательным требованиям. `<goal-complete>` сам по себе не служит доказательством.
4. **Объяснимость:** пользователь видит выбранную модель, причины ограничений, прогресс, полученный результат и полный счёт; подробные traces доступны отдельно.
5. **Экономичность:** оптимизировать стоимость успешной задачи при фиксированном качестве, а не минимальное число токенов. Compaction, дешёвая модель или fan-out могут уменьшить/увеличить итоговую цену.
6. **Удобство:** обоснованные defaults, сохранённые preferences, возможность поправить/отменить/продолжить; число вопросов и подтверждений измеряется вместе с качеством.

Для context: рассчитывать весь request вместе со схемами и мультимодальными inputs, а резерв output вычитать из окна до отправки. При long turn вызывать compaction/eviction на границах steps. Base64 length не равен количеству vision tokens.

Для agents: один договор о правах и бюджете дерева, независимые read versions, изоляция writers через checkout/worktree при нужной сложности, сохранённые step results и checks. Consensus использовать для поиска гипотез, verification — для установления фактов.

Для providers: покрытие заявленной связки модель/host/protocol, catalog freshness, проверяемое объяснение estimates, transport retry, полные contract errors. Не добавлять provider как «поддерживаемый», если работает только его список моделей.

## Порядок работ

| Этап | Содержание | Критерий завершения |
|---|---|---|
| 1. Сохранность и остановка | CORE-08/11, code mode permissions/isolation/RPC/cleanup, version guard для writes, atomic sessions | Fault injection не теряет данные; запрещённые действия не выполняются; очередь после abort не запускается; дочерние процессы заканчиваются |
| 2. Надёжная генерация | PCM/SSE, filenames/formats, validation, xAI flags/last frame, retry polling/download, durable job journal, media billing | При перезапуске восстанавливается известный job; сетевая ошибка не создаёт повторный POST; повреждённый файл не объявляется готовым |
| 3. Полный media workflow | Brief, endpoint capabilities, preview/QA, image edits, audio input/TTS, video storyboard/edit/export | End-to-end сценарии пользователя проверяются от задания до пригодного artifact |
| 4. Ядро и расширения | Goals/input, orchestration terminal states, MCP effects, context budget, точные ignores, registry abstractions | Полный suite стабилен; каждый mode имеет контракт, recovery и проверки результата |
| 5. Доказательства преимущества | Одинаковые задачи/модели, цена/качество/латентность, реальные providers и терминалы | Публикуемый воспроизводимый benchmark с ограничениями и сырыми результатами |

Не назначаю сроки без истории команды и замера масштаба изменений. Этапы отражают зависимости: художественный QA бесполезен, если успешный результат может потеряться.

## Как доказать «лучше других»

Нужны два отдельных сравнения: **harness при одной модели** и **готовый продукт с подбором моделей**. Первое измеряет реализацию workflow; второе — routing и совокупный результат. Нельзя объяснять выигрыш harness только более сильной моделью.

Предлагаемая стартовая батарея, ещё не проведённая:

- Code: 30 задач — исправление бага, refactor, multi-file feature, большой repo, flaky tests, interruption/resume, concurrent writes, provider failover. Одинаковые репозитории, snapshots и hidden assertions.
- Image: 20 briefs — обязательная кириллическая надпись, alpha, edit одной области, несколько references, consistent character, icon/asset set. Автопроверки плюс слепое человеческое предпочтение.
- Video: 15 briefs — vertical short, pinned frames, identity/motion continuity, silent request, storyboard, edit scene, interruption after submit, failed download/restart.
- Audio: 20 заданий — имена/числа/смешанный язык, дословная речь, длинный текст, clipping/silence, music loop, transcription/subtitles, оборванный stream.
- Resilience: fake clocks, reordered RPC responses, malformed SSE, 429/503, connection resets, disk full, rename failure, symlinks/junctions и process kill на каждой границе lifecycle.

Измерять: task success, обязательные требования, first-pass acceptance, human edits/questions, wall time p50/p95, фактическую стоимость всех попыток, duplicate paid jobs, recovery rate и потерю данных. Для творческого качества — несколько оценщиков с перемешанными анонимными результатами; для нестабильных метрик — повторы и интервалы неопределённости.

Предлагаемые release gates: ноль известных P0; весь fresh-build suite проходит стабильно; все критические regression/fault cases проходят; ни один подтверждённый job не требует повторной оплаты из-за локального restart; cost не выдаёт unknown за ноль; ни один повреждённый media artifact не помечается готовым. Это требования к продукту, не достигнутые показатели аудита.

## Отдельно о текущих тестах

`media-test` использует PNG из 11 байтов и строку `....ftypisom-fake-video`; `video-test` также работает с искусственными байтами. Это хорошие wire fixtures, но не декодируемые media fixtures. Добавить настоящие маленькие PNG/JPEG/GIF/WebP/WAV/MP4 и проверки чтения/декодирования, отдельно сохранить лёгкие mock-тесты формата API.

В `brain-test` готовность mock определяется sleep 1200 ms; readiness probe будет устойчивее. Его повторный standalone pass не доказывает отсутствие остальных багов, но не даёт основания объявить Brain сломанным по одному full-run failure.

В `goal-live` снова упали status, начало uncapped goal, начало hanging goal и число turns после Esc. Вывод показывает, что после ввода новой цели в одном сценарии осталась предыдущая `endless grind`. Нужно отдельно разобрать готовность input/editor между turns: это подтверждённый провал integration test, но корневая причина между гонкой теста и потерей пользовательского ввода ещё не установлена. Mock-сценарий `<FAIL>` в этом файле не формирует обещанный HTTP 400; его проверка может пройти от обычного turn budget и не подтверждает обработку ошибки API.

Следующее практическое действие — устранить этап 1, сохранив воспроизведения как regression cases, затем закончить lifecycle media. Новые модели и новые команды должны добавляться после этих гарантий.
