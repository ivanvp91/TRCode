# ТЗ: режим Cloud — синхронизация состояния между устройствами

Статус: черновик v1 (2026-08-23). Источник фактуры — инвентаризация локального
хранилища (`~/.trcode`), см. раздел 1.

Идея: важное состояние CLI — активная сессия, настройки, проекты, провайдеры,
выбранные модели, режим brain — живёт не только на машине, но и на облачном
сервере, и новое устройство подтягивает его одной командой.

Принцип: **offline-first**. Без сети и без облака CLI работает ровно как
сейчас; синхронизация — надстройка, которая может отвалиться, ничего не сломав.
Локальные файлы остаются источником истины на каждом устройстве, облако —
канал переноса.

---

## 1. Инвентарь: что вообще есть локально

Всё состояние лежит в `~/.trcode` (`TRCODE_HOME` переопределяет):

| Что | Где | Ссылка |
|---|---|---|
| Конфиг | `~/.trcode/config.json`, 0600 | `src/config.ts:339` |
| Креды провайдеров | `~/.trcode/auth/<provider>.json`, 0600 | `src/provider/credentials.ts:34` |
| Device id | `~/.trcode/auth/device-id` | `credentials.ts:84` |
| Сессии проекта | `~/.trcode/sessions/<projectKey>/<id>.json` | `src/config.ts:438`, `session.ts:76` |
| Input history | `~/.trcode/history/<projectKey>.json` | `src/session/history.ts:11` |
| Чекпоинты файлов | `~/.trcode/sessions/<key>/<id>.files/` | `src/session/checkpoint.ts:73` |
| Skills пользователя | `~/.trcode/skills/<name>/SKILL.md` | `src/skills/loader.ts:7` |
| Кэш каталога моделей | `~/.trcode/models.cache.json` | `src/provider/models.ts:284` |

Проектное (внутри репозитория, в облако не тянет само по себе):
`.trcode/memory.md`, `.trcode/skills/`, `.trcode/mcp.json`,
`.trcode/instructions.md`, `.trcode/artifacts/`.

Ключевое следствие из карты конфига: часть полей **машинно-специфична**
(`shell`, `newlineKeys`), часть — **карты по ключам**, которые надо мержить
поэлементно (`projectState`, `aliases`, `effortByModel`, …), а не заменять
целиком. `saveConfig()` уже умеет и то и другое (`replace[]`),
`src/config.ts:392`.

## 2. Область синхронизации

Состав того, что уходит в облако, управляется пользователем: проекты и сессии
можно **исключить из синхронизации целиком или по одному**, а Tier A-настройки
— отключить группой. Исключённое живёт только локально и в блобах сервера
не появляется вовсе (не «пустая запись», а отсутствие записи).

### 2.1 Выбор области

- `/cloud config` — интерактивное меню:
  - `settings` on/off — вся группа настроек Tier A одним флагом;
  - `providers` on/off — провайдеры/модели/brain-карты;
  - `projects` on/off + чёрный список ключей (`/cloud exclude <projectKey>`);
  - `sessions` on/off + лимит N последних на проект;
  - `history`, `skills` — on/off;
  - `files <projectKey>` on/off — **файлы проекта** (Tier F, раздел 2.3).
- Состояние выбора хранится локально (`~/.trcode/cloud/config.json`) —
  на каждом устройстве свой набор: рабочий ПК синхронизирует всё, ноут
  только настройки, VPS-агент ничего не выгружает, но читает.
- При выключении группы существующие блобы с сервера **удаляются** (tombstone),
  а не остаются висеть; повторное включение начинает заново с полного push.
- Исключение проекта убирает и его `projectState`, и его сессии/history.

### 2.2 Что входит по умолчанию

### Tier A — синхронизируется всегда

- **Настройки**: модель по умолчанию, `smallModel`, `effort*`, `lang`,
  `promptMode`, `permissions`, `thinkingRows`, `maxSteps`, `autoCompactAt`,
  `promptCache`, `skillsEnabled`, `skillAuto`, `memoryEnabled`, `instructions`.
- **Провайдеры и модели**: список подключённых провайдеров и их baseUrl/заголовки
  (`config.providers`, `defaultProvider`), `promptModels`, `subagentModels`,
  `brainModels`, `modelPrompts`, `pricing`, `contextWindows`,
  `hideIncompatibleModels`. **Без ключей** — см. Tier C.
- **Проекты**: карта `projectState[<projectKey>]` — последняя модель и effort
  каждого проекта, плюс человекочитаемое имя корня (новое поле, чтобы список
  проектов можно было показать на чужой машине). Отключается группой `projects`
  и точечно через `/cloud exclude`.
- **Aliases** и `mcpServers` (глобальный уровень).

### Tier B — синхронизируется по выбору (opt-in, `/cloud config`)

- **Сессии**: файлы `<id>.json` целиком (сообщения + usage + meta). Файлы
  append-only с уникальным id — конфликтов почти не дают, но тяжёлые и содержат
  код. Дефолт: последние N сессий на проект (N=5) либо выключено.
- **Input history** per project (500 строк) — удобно для «продолжить на ноуте».
- **Skills пользователя** (`~/.trcode/skills`) — вероятно Tier A, решить при
  реализации; риск — правки одного skill на двух машинах.

### 2.3 Tier F — файлы проекта: бэкап с ручной выгрузкой

Отдельная группа `files` (по умолчанию **выключена**): содержимое рабочего
дерева проекта уходит в облако как резервная копия. Это не двусторонняя
синхронизация в реальном времени, а **бэкап с явными командами**:

- **Выгрузка (backup) — автоматическая или по команде.**
  - `/cloud backup [projectKey]` (или сообщение в чате: «забэкапь файлы»,
    «синхронизируй файлы с облаком») — снимок рабочего дерева уходит на сервер.
  - При включённой группе и `/cloud config --auto-backup` — тихий инкрементальный
    push изменённых файлов после каждого turn (дебаунс, как у остальных групп).
- **Загрузка (restore) — только явно, никогда автоматически.**
  - `/cloud restore [projectKey]` / «восстанови файлы из облака» — перезаписывает
    локальные файлы содержимым сервера. Перед записью: предупреждение со счётчиком
    затираемых файлов и автоматический локальный чекпоинт текущего состояния
    (`src/session/checkpoint.ts`) — откат возможен через `/rewind`.
  - Частичный restore: `/cloud restore <key> <путь>` — один файл/каталог.
  - `/cloud diff [key]` — что отличается между диском и облаком (файл, размер,
    mtime/хеш), до того как что-то перезаписывать.
- **Что входит**: текстовые файлы рабочего дерева. Уважает `.gitignore`, если
  репозиторий есть; иначе встроенный deny-лист (`node_modules`, `.git`,
  `dist`, `target`, `.env*`, секреты, бинарники > лимита). Бинарники — по
  расширению-разрешённому списку (картинки, шрифты), остальное — текст.
- **Как хранится**: те же блобы, ключи `files/<projectKey>/<sha256>` —
  контентно-адресованное хранилище, дедупликация бесплатна; манифест
  `files/<projectKey>/manifest.json`: путь → {hash, size, mtime, deleted?}.
  Push кладёт только новые блобы и новый манифест; история — N последних
  манифестов (снапшотов), `/cloud restore` по умолчанию берёт последний.
- **Лимиты**: суммарный размер проекта (дефолт ~50 МБ) и размер файла (~2 МБ),
  настраивается на сервере; превышение — явная ошибка с подсказкой, что добавить
  в исключения, а не тихий обрезанный бэкап.
- **Не входит в автосинхронизацию настроек/сессий**: файлы живут своей жизнью —
  их push/restore никогда не запускается сам при обычном sync'е конфига.

Мотивация ручного restore: облачные файлы — страховка от потери машины и способ
переехать с ноута на ПК, а не канал, которым облако молча перезаписывает работу
на диске. Автоматическая выгрузка безопасна (диск — источник), автоматическая
загрузка опасна (облако становится источником) — поэтому она только по команде.

### Tier C — никогда не синхронизируется

- **Креды провайдеров** (`auth/*.json`): API-ключи и refresh-токены не покидают
  устройство в открытом виде ни при каких настройках по умолчанию. На другом
  устройстве провайдер виден как «подключён, но требует входа» (`/login`).
  Опциональное исключение — E2E-шифрованный бэкап ключей, см. раздел 6.
- `device-id`, `models.cache.json`, чекпоинты (`*.files/`), artifacts/spill,
  todo (in-memory), Orca-состояние, машинные поля `shell`/`newlineKeys`.

## 3. Архитектура

### 3.1 Клиент

Новый модуль `src/cloud/`:

- `store.ts` — снимок/восстановление локального состояния в нормализованную
  форму: плоские записи `{ key, body, rev, ts, deleted }`. Один ключ = один
  логический объект (например `config/settings`, `config/projectState/<key>`,
  `sessions/<projectKey>/<id>`). Карты конфига дробятся до поэлементных ключей —
  это основа бесконфликтного мерджа.
- `files.ts` — Tier F: обход рабочего дерева (gitignore/deny-лист), хеширование,
  сборка манифеста, push блобов, restore с чекпоинтом. Отдельный модуль,
  потому что у файлов другой контракт: контентно-адресованное хранилище вместо
  ревизий и только явные команды.
- `engine.ts` — цикл pull→merge→push, курсор изменений, дебаунс после
  `saveConfig`/`session.save` (не чаще раза в ~30 c), полный прогон при старте
  и по команде.
- `api.ts` — транспорт поверх нативного `fetch` (runtime-зависимости не
  добавляем), retry с backoff, работа офлайна без ошибок в интерфейсе;
  бинарные блобы файлов идут как base64 в JSON (лимиты раздела 2.3) либо
  raw-телом на том же эндпоинте — выбрать при реализации по тому, что проще
  серверу.

### 3.2 Сервер (self-hosted)

Минимальный сервис «версионированных блобов» `trcode-cloud`, без доменной
логики — весь мердж делает клиент. Однопользовательский: разворачивается одним
процессом Node (тот же стек, ноль зависимостей) на своём VPS/PaaS, хранилище —
файлы или SQLite. CLI не привязан к какому-либо центральному сервису
TokenRouter; сервер — обычная программа из npm/Docker, которую пользователь
запускает сам.

Управление ключами на сервере:

```
trcode-cloud key new [--read-only]   # печатает ключ один раз, хранит только SHA-256
trcode-cloud key list
trcode-cloud key revoke <id>
```

Первый запуск создаёт аккаунт с одним ключом; все устройства с этим ключом
делят одно пространство записей. Для сценария «ноут только читает» выдаётся
второй ключ с правом `read`.

Аутентификация: **API-ключ облака + self-hosting как основной сценарий.**
Никакого центрального сервиса и device flow: пользователь разворачивает сервер
на своём VPS, генерирует в нём ключ и подключает CLI одной строкой.

- `/cloud login <url> <ключ>` (или `trc cloud login`): URL сервера и ключ
  записываются в `~/.trcode/cloud/token.json`, 0600; ключ проверяется запросом
  `GET /v1/whoami`.
- Ключ — случайная строка (32+ байта, base64url), на сервере хранится только
  SHA-256-хеш. Один аккаунт = один ключ по умолчанию; опционально несколько
  именованных ключей с разными правами (`read`/`write`) для «ноут только читает».
- Ротация и отзыв: на сервере `trcode-cloud key new|revoke`. Устройство с
  отозванным ключом получает 401 и переходит в оффлайн-режим с пометкой в
  статусе.
- Смена сервера = повторный `/cloud login` с новым URL/ключом. Миграция
  состояния между своими серверами — обычным sync'ом клиента (подключился к
  новому пустому → push всего снимка).

Почему не device flow: у self-hosted сервера нет «второго уже авторизованного
устройства» и веб-кабини — подтверждать код просто некому и негде. API-ключ
выдаётся один раз на сервере, которым владеешь сам, и этого достаточно.

Транспорт: HTTPS обязателен для внешних адресов; **localhost и LAN —
равноправный режим работы**, не второсортный: на `http://localhost:*` /
`http://127.0.0.1:*` / адресах частных сетей (192.168.*, 10.*, *.local) клиент
работает по HTTP без флагов, для прочих нужен HTTPS или явный `--insecure`.
Так один и тот же сервер покрывает оба сценария: «облако» на VPS с доменом
и «локальный хаб» на своей машине/мини-ПК в домашней сети.

### 3.3 Протокол v1 (черновик контракта)

```
GET  /v1/changes?since=<cursor>        → { changes: [{key, rev, ts, deleted}], cursor }
GET  /v1/blob/<key>                    → { body, rev, ts }
PUT  /v1/blob/<key>?ifRev=<rev>        → { rev }   (409 при чужой ревизии)
DELETE /v1/blob/<key>?ifRev=<rev>      → 409-семантика та же
```

- `rev` монотонный на ключ; `PUT ifRev` — оптимистичная блокировка.
- Курсор `since` — сквозной по аккаунту; клиент хранит его локально
  (`~/.trcode/cloud/state.json`).
- Тела — JSON, лимит размера на запись (например 512 КБ; крупные сессии
  режутся на записи по сообщениям в v2, если понадобятся).

## 4. Разрешение конфликтов

1. **Скалярные поля настроек**: last-writer-wins по `ts`, ничья — по
   `deviceId` (лексикографически больший выигрывает). Лог: что чьё победило,
   показывается в `/cloud log`.
2. **Карты** (`projectState`, `aliases`, `brainModels`, …): мерж по ключам
   тем же LWW на элемент. Удаление элемента карты — tombstone-запись, чтобы
   удаление не проигрывало старой копии с другого устройства.
3. **Файлы-объекты** (сессия, skill): id уникален по построению — конфликт
   практически невозможен; правка одного файла на двух машинах (переименование
   сессии) решается LWW по `updatedAt`.
4. **Удаление сессии**: tombstone в облаке; локально удаляется на других
   устройствах при следующем pull. Гарантия: облако никогда не resurrect
   запись старше tombstone.
5. **Конфигурация, меняющая поведение рантайма** (`maxSteps`, `trim*`):
   синхронизируется, но локальная правка, сделанная «здесь и сейчас» во время
   активного turn, не перетирается посреди хода — применение отложенного пула
   ждёт конца turn.
6. **Разные области на устройствах**: исключение локально — это «не выгружать
   своё» (push молчит), а не «удалить в облаке»; pull при этом применяется
   полностью. Так ноут без группы `projects` не стирает проекты рабочего ПК.
   Явное удаление из облака — только tombstone'ом от устройства, у которого
   группа включена (или командой `/cloud config` при выключении группы).

## 5. Поведение в UI

- Команды: `/cloud login <url> <ключ>`, `/cloud logout`, `/cloud status`
  (сервер, последняя синхронизация, что включено), `/cloud sync` (ручной
  прогон), `/cloud on|off`, `/cloud config` (группы: settings/providers/
  projects/sessions/history/skills/files; лимит сессий),
  `/cloud exclude <projectKey>` и `/cloud include <projectKey>` — точечное
  исключение проекта, `/cloud exclude` без аргумента — список исключённого.
- Файлы проекта (Tier F): `/cloud backup [key]`, `/cloud restore [key] [путь]`,
  `/cloud diff [key]`, `/cloud snapshots [key]` (список снапшотов).
  Те же действия понимаются и в обычном сообщении чата: «забэкапь файлы»,
  «синхронизируй файлы с облаком», «восстанови файлы из облака» — модель
  вызывает те же команды/инструменты; restore без явного подтверждения запрещён.
- Автоматика: полный sync при старте REPL (тихо, в фоне, до первого ввода
  не блокирует), push с дебаунсом после изменений, pull — по таймеру раз в
  несколько минут и перед стартом turn. Файлы — вне этой автоматики, кроме
  включённого `--auto-backup`.
- Индикация: одна строка в статусе (`cloud: synced 12:41`); ошибка сети —
  тихая пометка, не warn на каждый ход; 401 — «ключ отозван, /cloud login».
- Первый login на новом устройстве: вопрос «скачать облако / начать с пустого /
  выгрузить это устройство» — три явных варианта вместо угадывания.
- `trc cloud ...` — те же действия из one-shot режима и скриптов.

## 6. Безопасность

- Транспорт: HTTPS обязателен для внешних адресов; localhost и частные сети —
  по HTTP без флагов (см. раздел 3.2). Ключ облака в
  `~/.trcode/cloud/token.json`, 0600; в запросах — `Authorization: Bearer`.
- Креды провайдеров по умолчанию не синхронизируются (Tier C). Сам сервер
  пользовательский, но правило не меняем: VPS — не повод возить ключи провайдеров
  в открытом виде.
- Опция `/cloud config --secrets`: E2E-шифрование выделенного секрета-блоба
  (`auth/*`) парольной фразой: AES-256-GCM, деривация scrypt, фраза не
  покидает устройства, сервер видит шифротекст. Выключено по умолчанию;
  включение — с явным предупреждением, что потеря фразы = потеря ключей.
- Отзыв ключа мгновенно запрещает устройству изменения (401); данные на нём
  остаются локальными.
- В логах и в `/debug` тела блобов и сам ключ не печатаются, только ключи
  записей и ревизии.

## 7. Критерии приёмки

| # | Проверка |
|---|---|
| A1 | Машина A: настройка моделей/brain/проектов → машина B: `/cloud login <url> <ключ>` → `/cloud sync` → `/models`, `/stat`, `/help` показывают то же состояние; `diff ~/.trcode/config.json` сходится по Tier A-полям |
| A2 | Активная сессия A (Tier B вкл.) продолжается на B: `/resume` находит сессию по title/id, история воспроизводится |
| A3 | Провайдер с ключом только на A виден на B как «requires login», ничего не течёт: в блобах сервера нет `accessToken`/`apiKey` (тест-инспекция payload'а) |
| A4 | Одновременные правки (A и B меняют модель разных проектов) — оба изменения выживают после sync |
| A5 | Оффлайн: при недоступном сервере CLI работает без ошибок в интерфейсе; при возврате сети догоняет |
| A6 | Удаление сессии на A не воскресает после sync с B (tombstone) |
| A7 | Ключ отозван на сервере → клиент получает 401, переходит в оффлайн с пометкой; повторный login новым ключом продолжает работу без потери локальных данных |
| A8 | HTTP-адрес отклоняется для внешних хостов; `http://localhost`, `127.0.0.1` и адреса частных сетей (192.168.*, 10.*, *.local) работают по HTTP без флагов — один и тот же сервер доступен и как VPS-облако, и как локальный/домашний хаб |
| A9 | `/cloud exclude <key>`: проект исчезает из блобов сервера после sync; на другом устройстве его projectState/сессии не появляются. Выключение группы удаляет её старые блобы (tombstone), повторное включение восстанавливает полным push |
| A10 | Разные наборы групп на устройствах не дерутся: ноут без `projects` не стирает проекты, выгруженные ПК (pull применяется, push своих исключений не происходит) |
| A11 | Tier F backup: `/cloud backup` кладёт манифест + блобы; повторный backup после правки одного файла пушит только его (контентная адресация); `.gitignore`/deny-лист уважается; превышение лимита — явная ошибка |
| A12 | Tier F restore: `/cloud restore` без подтверждения не пишет ничего; перед записью создаётся чекпоинт, `/rewind` возвращает исходное состояние; `/cloud diff` показывает расхождения до действия |
| A13 | Restore **никогда** не запускается автоматически: обычный sync при включённой группе `files` не трогает рабочий диск ни при каком расхождении |
| A14 | Все существующие тесты зелёные; новые suite'ы: `test/cloud-store-test.mjs`, `test/cloud-merge-test.mjs`, `test/cloud-files-test.mjs`, интеграционный против mock-сервера по образцу `test/mock-server.mjs` |
| A15 | Runtime-зависимости не появились (`package.json` dependencies: 0, и у сервера тоже) |

## 8. Non-goals (v1)

- Не делаем веб-кабину, регистрацию и многопользовательность: сервер
  однопользовательский, владелец = оператор VPS.
- Не делаем двустороннюю файловую синхронизацию в реальном времени (Dropbox-style):
  файлы — бэкап с явным backup/restore, не постоянный канал.
- Не синхронизируем чекпоинты/artifacts, realtime-collab на сессии,
  end-to-end-шифрование всего бэкапа (только опциональный секрет-блоб).
- Не поддерживаем сторонние бэкенды (WebDAV/S3) — адаптер возможен в v2,
  если спрос появится; протокол специально тонкий.
- Не переносим OAuth-сессии провайдеров: refresh-токены у большинства хостов
  одноразовые и привязаны к клиенту — технически бессмысленно.

## 9. Порядок внедрения

0. **Execution-world seam** (перенесено из TZ-harness-adoption.md, этап 4;
   делается ДО всего остального). Урок deepseek-harness: файловая система и
   запуск процессов должны жить в одном «мире исполнения», тогда облачный
   режим — это замена одного провайдера, а не правка семи файлов.
   - `src/exec/world.ts`: интерфейс
     `{ readFile, writeFile, list, glob, grep, runShell, snapshot }` +
     реализация `localWorld()` поверх текущих fsutil/shell/shellsnap.
   - Инструменты `files.ts` / `search.ts` / `shell.ts` и модули cloud-области
     (`store.ts`, будущий `files.ts`) получают world через ToolContext.
     Рефакторинг 1:1 — поведение не меняется; полный прогон test/run-all.mjs.
   - Чекпоинты (checkpoint.ts) продолжают перехватывать записи на уровне
     tools, а не node:fs — там ничего менять не нужно (проверить при
     реализации).
   - Позже, на этапе Tier F/удалённой песочницы: `remoteWorld()` как вторая
     реализация того же интерфейса — и Bash, и чтение, и запись переезжают
     вместе, без fork'ов провайдеров.

1. `src/cloud/store.ts` — нормализация локального состояния в ключи/записи +
   обратная сборка с учётом области (`scope`: какие группы/проекты включены);
   тесты на идемпотентность (snapshot → restore == identity) и на то, что
   исключённое не попадает в снимок вовсе.
2. Мерж-движок (правила раздела 4) поверх записей, без сети; таблица тестов
   на конфликты (A4/A6/A10).
3. Mock-сервер + `api.ts` (детект localhost/LAN для HTTP), engine с курсором
   и дебаунсом; интеграционные тесты (A5/A8).
4. Команды `/cloud *` (включая `/cloud exclude|include`, `/cloud config`),
   login по ключу, индикация в статусе.
5. Tier B (сессии/history) поверх работающего Tier A.
6. Tier F (`files.ts`): обход дерева/хеши/манифест, backup/restore/diff,
   чекпоинт перед restore; тесты A11–A13 на временных каталогах.
7. Сервер `trcode-cloud`: отдельный репозиторий, один процесс Node (тот же
   стек, ноль зависимостей), хранилище — файлы или SQLite; Dockerfile +
   docker run на VPS за caddy; документация самостоятельного хостинга
   (генерация ключа, HTTPS, бэкап каталога хранилища) в README.

Этапы 1–2 дают проверяемую ценность без сервера (локальный журнал изменений);
сервер подключается, когда мерж покрыт тестами.
