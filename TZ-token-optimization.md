# ТЗ: оптимизация входных токенов

Источник: анализ сессии 2026-08-01. Проблема: большое потребление input-токенов,
включая короткие сессии — зафиксировано 200k input на первом сообщении и turn со
статистикой **↑61k sent / ↓1.4k received** на простой ответ без tool-шагов.

Ограничение: все меры — **без изменения reasoning effort** и **без потери качества**
(не выбрасываем данные, которые модель ещё не успела использовать).

---

## 1. Диагноз

Input растёт по трём независимым причинам:

1. **Квадратичный рост в agent loop.** Каждый шаг пересылает всю историю
   (`src/session/trim.ts:1-12`). N шагов по ~40k = N·40k суммарного input.
   Число 200k «на первом сообщении» — это обычно 4-5 tool-шагов, а не один запрос.
2. **Tool output оседать в истории целиком.** `read` отдаёт до 400KB/2000 строк
   (`src/tools/files.ts:8-9`), shell — до 60k символов (`src/tools/shell.ts:7`).
   Весь этот объём уходит в каждый последующий запрос, пока не сработает trim
   при превышении `maxRequestTokens` (default 40k).
3. **Непрозрачность.** Из status line (↑61k) непонятно: это один запрос или сумма
   по шагам, сколько из этого кэшировано провайдером, сколько занимает системный
   промпт и схемы инструментов, сколько — история. Без разбивки оптимизировать
   нечего.

Зафиксированный baseline для сверки: системный промпт + env + workspace listing
+ 10 tool-схем ≈ 4-6k токенов (`src/agent/prompt.ts`, `src/tools/index.ts`).
Всё сверх этого на первом запросе — история, tool output или серверная надбавка.

## 2. Требования

### T1. Конфигурируемые конфиг-дефолты (без правок кода)

```json
{
  "maxRequestTokens": 25000,
  "maxSteps": 12,
  "autoCompactAt": 0.6
}
```

- `maxRequestTokens: 25000` — по замерам проекта экономит ~41% байт запросов
  (README, таблица «Token spend»). Стоп-сигнал: если модель начнёт перечитывать
  уже прочитанные файлы — вернуть 40k.
- `maxSteps: 12` — обычная задача решается за 3-5 шагов; 60 (`src/config.ts:133`)
  даёт runaway loop потолок 2.4M input. На `max_steps` луп останавливается
  штатно (`src/agent/loop.ts:208`).
- `autoCompactAt: 0.6` — реальный триггер `min(window·0.6, 2·maxRequestTokens)`
  (`src/session/compact.ts:143-149`); снижение budget автоматически раньше
  компактит историю в дайджест.

### T2. Вынести параметры trim в конфиг

Сейчас захардкожены (`src/session/trim.ts:50-51`): `keepRecent = 8`,
`minTrimBytes = 400`.

- Добавить в `Config` (`src/config.ts`): `trimKeepRecent?: number`,
  `trimMinBytes?: number` с теми же дефолтами.
- Передавать из `runAgent` (`src/agent/loop.ts:141-143`).
- Рекомендуемое значение для экономного профиля: `trimKeepRecent: 4`.

### T3. Жёсткий per-result cap на tool output

Trim срабатывает только когда вся история превысила бюджет — до этого момента
один большой дамп гоняется по шагам без ограничений.

- В `trimForRequest` (`src/session/trim.ts`): любой tool result длиннее
  `maxToolResultBytes` (новый конфиг, default ~8_000) схлопывается до первых
  ~2_000 байт + stub-пометка **независимо от общего бюджета**, кроме результатов
  последнего шага (keepRecent).
- Формат stub тот же, что сейчас: head + «[N more characters omitted… Call the
  tool again if you need it in full.]» — pairing `tool_call ↔ tool` не ломать.

### T4. Разбивка токенов в /cost и отладка первого запроса

- `/cost`: показывать отдельно fresh input и cached (поле `cached_tokens` уже
  собирается, `src/usage.ts:30-35`, `src/provider/client.ts:490`). Если cached
  у kimi-k3 стабильно 0 — кэш провайдера по пути не работает, фиксируем как факт.
- Новая команда `/debug request` (или флаг `TRCODE_DEBUG=1`): для последнего
  запроса печатать оценку `estimateTokens` по секциям — system prompt, tool-схемы,
  user/assistant сообщения, tool results. Это ответит на вопрос «откуда 61k»
  без внешних инструментов.
- Status line / turn summary: рядом с суммой выводить число запросов
  (`requests` уже есть в `UsageTracker.totals()`, `src/usage.ts:94-120`), чтобы
  ↑61k при `requests: 4` читалось как ~15k/запрос.

### T5. Ранняя компакция и дисциплина сессий

- `/compact` вручную между логическими задачами; `/new` вместо бесконечной сессии.
- После T1 компакция начнёт срабатывать автоматически на ~50k истории
  (2 × 25k budget).

### T6. Широкая разведка — только через субагентов

- Прочитанное read-only субагентом не попадает в историю ведущего агента —
  возвращается только финальный текст (`src/agent/subagent.ts:1-9`).
- Добавить в `AGENTS.md` проекта инструкцию: перед исследованием больше ~3 файлов
  — `task` с `read_only: true`. Промпт это уже поощряет
  (`src/agent/prompt.ts:28-30`), но k3 по умолчанию делает это редко.
- Изменений кода не требует.

### T7. Гигиена tool-использования (промпт-уровень)

В base prompt (`src/agent/prompt.ts`) уже есть; контролируется ревью поведения:

- `read` вместо `cat` через shell; большие файлы — offset/limit.
- `edit` вместо `write` всего файла.
- Один файл — один read за сессию (перечитывание = симптом слишком
  агрессивного trim, см. стоп-сигнал T1).

### T8. Стабильный префикс для prompt caching

Не ломать начало запроса между шагами — иначе провайдерский кэш бесполезен:

- Системный промпт собирается один раз и не должен меняться внутри сессии
  (сейчас так, `src/ui/repl.ts:449`).
- Trim (T3) применять только к старым сообщениям, строго после keepRecent —
  текущее поведение сохранить: hysteresis защищает горячий префикс.
- Проверка: после T4 в `/cost` у k3 должен появиться ненулевой cached input
  начиная со второго шага. Если нет — вопрос к TokenRouter, не к коду.

## 3. Критерии приёмки

Замеры — `test/measure-tokens.mjs` (расширить сценариями T3) и live-прогоны:

| Метрика | Было | Цель |
|---|---|---|
| Простой turn без tools ( «hi» после T4-разбивки ) | ↑ до 61k | ≤ 6k input, `requests: 1` |
| 12-round tool-heavy сессия (`measure-tokens.mjs`) | −32% при 40k | −41..45% при 25k + T3 |
| Ни один tool-call/tool pairing не сломан | — | mock protocol-test зелёный |
| Модель не перечитывает файлы чаще, чем раньше | — | визуальный контроль транскрипта |

Регрессия качества = перечитывание уже прочитанного или потеря нити задачи.
Обнаружена — откатить `maxRequestTokens` до 40k и `trimKeepRecent` до 8.

## 4. Non-goals

- Не менять дефолтный effort (`high`) и не трогать reasoning-пайплайн.
- Не удалять сообщения из истории, не ломать `tool_call ↔ tool`.
- Не поддерживать prompt caching API-вызовами (серверная зона TokenRouter) —
  только измерить и не мешать.
- Не вводить RAG/векторный поиск по истории.

## 5. Порядок внедрения

1. T4 (разбивка/дебаг) — сначала измерить, иначе остальное вслепую.
2. T1 (конфиг) — нулевой код, мгновенный эффект.
3. T2 + T3 (trim), прогон `npm test` и `test/measure-tokens.mjs`, обновить
   таблицу в README.
4. T6-T8 — промпт/эксплуатация, по факту замеров.

## 6. Статус и поправки (2026-08-01)

### Сделано

**T4 — измерение.** Строка после хода теперь показывает сумму по всем запросам
хода, а не последний: `↑61k in 4 requests · 48k cached`. Счётчик живёт в
`UsageTracker.beginTurn()/turnTotals()` (`src/usage.ts`) и включает субагентов.
В `/cost` добавлены колонки **per req** и **cached**; при нуле cached на
anthropic-модели печатается объяснение.

**T8 — prompt caching, но не так, как в ТЗ.** См. поправку ниже: без
`cache_control` Anthropic не кэширует ничего. Добавлены breakpoint'ы на
системный промпт, последнюю схему инструмента и конец истории
(`src/provider/anthropic.ts`), с порогом 2048 токенов — ниже него запись в кэш
дороже выгоды. Ключ конфига `promptCache` (по умолчанию `true`); если хост
отвечает 400 на `cache_control`, поле снимается и запрос повторяется один раз.

Замер на живом API, промпт 4834 токена, два одинаковых запроса подряд:

| Запрос | input | из них cached |
|---|---|---|
| первый | 4834 | 0 |
| повтор, `promptCache: false` | 4834 | 0 |
| повтор, по умолчанию | 4834 | **4832** |

То есть TokenRouter `cache_control` **пропускает** — вопрос из T8 закрыт.

**Волатильный префикс.** Листинг корня в системном промпте пересобирался каждый
ход; один новый файл менял префикс и обнулял кэш для всей истории. Теперь
снимок на директорию (`src/agent/prompt.ts`), сбрасывается по `/cwd`.

### Поправки к диагнозу

1. **↑61k — это один запрос, а не сумма.** `statusLine` читал `usage.lastTurn`,
   которое перезаписывается на каждом запросе. Значит, история действительно
   весила 61k в одном запросе — и наоборот, для многошагового хода строка
   **занижала** расход. Исправлено (см. T4).
2. **`autoCompactAt: 0.6` на 1M-окне ничего не даст.** Триггер —
   `min(window·ratio, 2·maxRequestTokens)`; при 25k связывающий член 50k против
   600k. Крутить надо `maxRequestTokens`.
3. **Trim не трогает обычный текст** — только tool-результаты. Длинная
   переписка без инструментов идёт целиком до самой компакции; T3 на этот
   сценарий не влияет.
4. **Non-goal «не поддерживать prompt caching API-вызовами» — неверна** для
   anthropic-пути: без breakpoint'ов кэша нет вообще. Для openai-протокола
   формулировка верна, там кэш автоматический.

### Осталось / замечания к оставшимся пунктам

- **T1**: `maxSteps: 12` — сомнительная экономия. Упёршись в потолок, вы
  говорите «continue», и вся история уходит заново; потолок ограничивает
  катастрофу, а не расход. Разумнее 30-40.
- **T3**: жёсткий cap 8k→2k head столкнётся с собственным стоп-сигналом из T1 —
  модель начнёт перечитывать. Резать надёжнее на источнике: дефолтный `limit`
  у `read`, head+tail у `shell`.
- **Дедупликация перечитываний**: `readFiles` в `ToolContext` уже ведётся —
  можно отвечать «файл не менялся с прошлого чтения» вместо повторного дампа.
- Критерий «≤6k на простой turn» достижим только в свежей сессии; для
  продолженной надо мерить накладные расходы поверх истории.
